# AI 아키텍처 — LLM 오케스트레이션 구조

> **기준일:** 2026-10-30  
> **기준 자료:** `ai-architecture.pdf` (7페이지), `ai-hiring-platform` 브랜치의 구현 설명  
> **관련 문서:** ADR-0003, ADR-0005, ADR-0006, ADR-0008, ADR-0013, ADR-0014, TRD 05  
> **문서 범위:** 특정 AI 모델·버전의 선정이 아닌 LLM 작업 분리, 호출 경로, 검증, 큐 운영 및 실패 처리 구조

## 1. 문서 개요

본 문서는 AI 기반 1차 채용면접 플랫폼의 **LLM 오케스트레이션 구조**를 소개합니다. AI 모델들이 서로 직접 대화하거나 호출하는 구조가 아니라, **애플리케이션 코드(API·worker·scheduler)가 단일 목적의 AI 태스크(T1~T8)를 호출**하고 출력값을 검증한 뒤 다음 작업에 전달합니다.

LLM은 문장 생성과 항목별 평가를 담당하고, **점수 합산·가중치·반올림은 코드**가 수행합니다. **최종 채용 결정은 채용 담당자**가 내리며, LLM이 합격·불합격을 판단하거나 추천하지 않도록 제한합니다.

## 2. 주요 설계 원칙

| 구분 | 원칙 | 관련 구현 |
|---|---|---|
| P1 | 점수 계산은 LLM이 아닌 결정적 코드에서 처리 | `evaluation/scoring.py` |
| P2 | JSON 스키마 강제 후 Pydantic 재검증 | `ai/tasks/base.py` |
| P3 | LLM 인용은 원문 위치를 확인한 경우에만 인정 | `evaluation/quotes.py` |
| P4 | 무응답·짧은 답변·꼬리질문 한도는 LLM 호출 전 규칙 검사 | `TaskSpec.preflight` |
| P5 | 태스크별 최소 데이터만 전달하고 평가에서 개인정보·이력서 제외 | `pipeline.unit_input`, `_feedback` |
| P6 | 실시간 처리와 배치 평가를 서로 다른 LLM 서버로 분리 | `ai/direct.py`, `LANE_SERVER` |
| P7 | 모델·프롬프트·옵션·루브릭·규칙 버전을 manifest 해시로 관리 | `ai/manifest.py` |
| P8 | 긴 모델 호출 중 DB 트랜잭션 유지 금지 | `jobs/handlers.py`, `interview/turns.py` |
| P9 | 합격·불합격 판단 및 추천은 LLM에서 금지 | `TaskSpec.system_prompt`, `textrules.has_p8` |

## 3. 구성 요소 및 실행 환경

| 구성 요소 | 역할 | 처리 장치 | 컨테이너 |
|---|---|---|---|
| 실시간 LLM | RT 꼬리질문 판단, INTERACTIVE 질문 구성·이력서 추출 (동시 슬롯 2개) | GPU | `llm-rt` |
| 평가 LLM | BATCH 답변 평가·총평·피드백·코드 리뷰 (동시 슬롯 1개) | CPU | `llm-eval` |
| STT | 음성 → 텍스트 | GPU | `stt` |
| TTS | 질문 텍스트 → 48 kHz PCM 음성 | CPU | `tts` |
| 임베딩 | 생성 질문 중복 검사(코사인 유사도 0.85 이상) | CPU | `embed` |
| 오케스트레이터 | API 요청, 비동기 작업, 스케줄 관리 | - | `api`, `worker`, `scheduler` |

LLM 런타임은 현재 **OpenAI 호환 llama.cpp 서버**를 사용하지만, `chat(messages, schema, options)` 인터페이스로 추상화되어 있어 다른 런타임으로 교체할 수 있습니다.

`AIHIRE_AI_MODE`는 `direct`(현재 배포), `service`(로컬 개발), `fake`(구성 점검 전용, 운영 불가)를 지원합니다.

### 3.1. 처리 레인

| 레인 | 용도 | 기본 데드라인 | 실행 서버 |
|---|---|---|---|
| `RT` | 면접 중 꼬리질문 결정 | 5초 | 실시간 LLM |
| `INTERACTIVE` | 면접 질문 구성·이력서 추출 | 120초 | 실시간 LLM |
| `BATCH` | 답변 평가·리포트·피드백·코드 리뷰 | 600초 | 평가 LLM |

Gateway는 **RT > INTERACTIVE > BATCH** 순으로 우선순위를 관리합니다. 동일 서버에서 상위 레인 요청이 도착하면 하위 레인 작업을 선점할 수 있습니다.

## 4. LLM 호출 계층

```text
API / 면접 세션 / Worker
       │
       ▼
AIClient (레인 라우팅, 데드라인, 장애 변환, manifest)
       │
       ▼
run_task (preflight, split/merge, 재시도, fallback)
       │
       ▼
Gateway (우선순위, 선점, 서버 상태 확인)
       │
       ▼
LLM 서버 (JSON schema 기반 응답)
       │
       ▼
Pydantic 검증 + check() → Outcome → 호출자
```

각 태스크의 `TaskSpec`은 프롬프트, 출력 스키마, 모델 옵션, 검증기, 재시도 한도를 관리합니다. 인프라 장애는 `AIUnavailable`로 변환하여 처리합니다.

## 5. AI 태스크 카탈로그

| ID | 태스크 | 레인 | 역할 및 주요 검증 |
|---|---|---|---|
| T1 | `resume_extract` | INTERACTIVE | PDF 텍스트에서 이력서 정보 추출, 원문에 없는 값 제거; 실패 시 직접 입력 |
| T2 | `question_generate` | INTERACTIVE | 공고·회사 소개 기반 질문 생성, 인용·금지어·중복 검증; 부족하면 질문은행 보완 |
| T3 | `resume_question` | INTERACTIVE | 이력서 기반 질문 생성; 근거 없으면 직무 질문은행으로 대체 |
| T4 | `followup_decide` | RT | `ASK` / `SKIP` 결정; 5초 이내, 검증 실패 시 SKIP |
| T5 | `evaluate_answer` | BATCH | 4개 평가 항목별 인용·코멘트·1~5점 생성; 근거 부족 시 `INSUFFICIENT` |
| T6 | `report_summary` | BATCH | 문항별 결과를 바탕으로 총평·강점·개선점 생성; 합불 표현 금지 |
| T7 | `candidate_feedback` | BATCH | 지원자용 피드백 작성; 점수·순위·인용·가중치 비공개 |
| T8 | `code_review` | BATCH | 제출 코드에 대한 설명형 리뷰; 숨김 테스트 비공개, 점수 영향 없음 |

모든 사용자 입력은 nonce 펜스로 구분하고 프롬프트 인젝션 의심 여부를 표시합니다. 기본 `seed=42`, 평가 태스크 `temperature=0`으로 설정하며, 생성 태스크 T2·T4에는 별도 온도를 적용합니다.

## 6. 주요 서비스 흐름

### 6.1. 지원 및 이력서 추출

`PDF 업로드 → extract_resume 작업 → T1 → 지원서 자동 입력 → 지원자 확인 후 제출`

### 6.2. 면접 질문 준비

`면접 시작 요청 → compose_questions → T2/T3 및 질문은행 → 임베딩 중복 검사 → 10문항 확정 → tts_pregen`

질문 구성은 **기업 2문항, 직무 4문항, 인성 2문항, 이력서 2문항**을 기준으로 합니다. 인성 질문은 질문은행을 우선 활용하고 부족분을 생성합니다. 확정된 10문항 세트는 변경하지 않습니다.

### 6.3. 실시간 면접

`질문 TTS 재생 → 지원자 음성 → VAD → STT → 개인정보 마스킹된 eval_text → T4 꼬리질문 판단 → ASK 또는 SKIP`

- 꼬리질문은 **본질문당 최대 1개, 전체 최대 4개**입니다.
- 무응답·내용 없음 등은 LLM 호출 없이 SKIP합니다.
- T4 타임아웃·검증 실패·서버 장애가 발생해도 면접을 중단하지 않고 SKIP하며 사유를 기록합니다.
- 답변 확정 시 `pre_evaluate`를 outbox에 등록하여 T5 사전 평가를 별도 평가 서버에서 비동기로 수행합니다.

### 6.4. 제출 후 평가

`evaluate_application → 사전 평가 재사용 여부 확인 → 필요 시 T5 → 코드 점수 계산 → T6 총평 → T7 피드백 → T8 코드 리뷰 → 리포트 저장 → 담당자 검토·결정`

사전 평가와 현재 manifest가 일치하는 경우에만 결과를 재사용합니다. 코딩 채점이 완료되지 않았다면 평가를 연기합니다. T6과 T7은 서로 다른 입력으로 별도 호출하여 담당자용 정보가 지원자에게 유출되지 않도록 합니다.

## 7. 비동기 작업 큐

| 작업 | 리소스 큐 | 우선순위 | 최대 시도 | 사용 AI |
|---|---|---:|---:|---|
| `compose_questions` | LLM | 10 | 3 | T2, T3, 임베딩 |
| `tts_pregen` | CPU | 15 | 3 | TTS |
| `extract_resume` | LLM | 20 | 2 | T1 |
| `grade_coding` | RUNNER | 20 | 3 | 샌드박스 실행, AI 없음 |
| `pre_evaluate` | LLM_EVAL | 40 | 2 | T5 |
| `evaluate_application` | LLM_EVAL | 50 | 2 | T5~T8 |

PostgreSQL `jobs` 테이블을 원본 데이터와 outbox로 사용하며, dispatcher가 Redis sorted set으로 작업을 배분합니다. worker는 PostgreSQL lease를 확보한 후 실행합니다. Redis 장애 시 SQL claim으로 대체합니다. `AIUnavailable`은 시도 횟수를 차감하지 않고 연기하며, 평가가 2회 실패하면 `ON_HOLD` 상태로 전환합니다.

## 8. 품질·보안 및 실패 대응

- **구조화 출력:** JSON schema 강제 → Pydantic 검증 → 형식 재시도.
- **근거 검증:** LLM이 제시한 인용을 원문과 대조하고, 불일치 시 재생성 또는 근거 부족 처리.
- **금지 질문:** 차별·사적 질문 규칙(`fq-1`)으로 질문과 꼬리질문 검사.
- **개인정보 최소화:** 평가 입력에서 이름·연락처·나이·성별 언급 마스킹, 이력서는 평가 입력에서 제외.
- **정보 유출 방지:** 지원자 피드백에 점수·인용·가중치 제외, 코드 리뷰에 숨김 테스트 제외.
- **합불 판단 제한:** 시스템 프롬프트와 P-8 출력 검사로 합불 판단·추천 차단.
- **재현성:** manifest 해시를 평가 실행 이력과 함께 저장.

| 장애 상황 | 실시간 T4 | 비동기 작업 |
|---|---|---|
| LLM 서버 다운 | `SKIP(INFRA)` | 시도 횟수 미차감 후 연기 |
| 데드라인 초과 | `SKIP(TIMEOUT)` | 시도 1회 차감 |
| 출력 검증 실패 | `SKIP(INVALID)` | 재시도 후 실패 시 시도 차감 |
| 평가 2회 실패 | 해당 없음 | `ON_HOLD`, 담당자 재평가 |

## 9. 알려진 한계 및 후속 과제

1. **평가 처리 지연:** 평가 LLM이 CPU에서 실행되어 T5는 수십 초, 전체 평가는 수 분이 걸릴 수 있습니다. GPU 확보 시 BATCH 레인 이전을 검토합니다.
2. **질문 생성 트랜잭션:** `compose_questions`가 LLM 호출 중 DB 트랜잭션을 유지하는 부분을 읽기·호출·쓰기 단계로 분리해야 합니다.
3. **STT 환각:** 무음 구간의 잘못된 인식 사례가 있어 VAD 임계값과 무음 필터 개선이 필요합니다.
4. **총평 문장 분류:** T6에서 최저점 항목을 강점으로 분류한 사례가 있어 프롬프트·검증 규칙 보강이 필요합니다.
5. **실시간 처리 확장:** RT와 INTERACTIVE가 두 개의 LLM 슬롯을 공유하므로 동시 면접 증가 시 RT 전용 서버 분리를 검토합니다.

## 10. 문서 범위 및 별도 확인 사항

이 README는 첨부된 **LLM 오케스트레이션 아키텍처 문서**를 요약한 것으로, 프로젝트 전체 AI 기능을 새롭게 확정하는 문서는 아닙니다.

- **AI 채용공고 초안 생성:** 전체 프로젝트 요구사항에 포함된 기능이지만, 첨부 문서의 T1~T8 카탈로그에는 별도 태스크로 정의되어 있지 않습니다. 공고 생성용 태스크와 검증·관리자 승인 흐름은 후속 아키텍처에서 정의할 필요가 있습니다.
- **최종 채용 결정:** 이 문서에서는 AI 자동 합불 판정이 아닌 **채용 담당자의 최종 결정**을 원칙으로 합니다. 다른 PRD·TRD의 판정 정책과 차이가 있다면 정합성 검토가 필요합니다.
- **LangGraph 사용 여부:** 첨부 문서는 애플리케이션 코드 기반 오케스트레이션을 설명하며, LangGraph 기반 실행 구조를 명시하지 않습니다.
