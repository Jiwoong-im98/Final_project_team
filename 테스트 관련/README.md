# AI 1차 채용면접 자동화 플랫폼 — 테스트 문서

## 1. 개요

본 디렉터리는 **AI 1차 채용면접 자동화 플랫폼**의 테스트 계획서와 테스트 케이스를 관리합니다. 지원자의 회원가입과 지원부터 AI 면접, 코딩테스트, AI 채점·1차 합격 결정, 결과 공개 및 데이터 삭제까지의 동작을 검증하기 위한 문서입니다.

테스트 계획서는 **무엇을, 어떤 환경과 기준으로 검증할지** 정의하며, 테스트 케이스는 해당 계획을 **어떤 입력·절차와 예상 결과로 확인할지** 구체화합니다. 두 문서는 상호 보완 관계이며, 구현 및 테스트 과정에서 발견된 이슈에 따라 갱신될 수 있습니다.

## 3. 테스트 계획서 (v0.1)

### 목적 및 범위

서비스의 주요 업무 흐름이 정상적으로 연결되는지 확인하고, 장애·화면 이탈·마감 상황의 처리, AI 평가 근거, 결과 공개 시점 및 데이터 보관 정책을 검증합니다. **PRD의 완성 기준 AC-01~AC-23**과 연계하여 검증하는 것을 목표로 합니다.

### 핵심 테스트 시나리오

1. **가입·로그인·지원 준비:** 입력 항목, 권한, 중복 지원·응시, 이력서 추출, 필수 동의 및 장치 점검
2. **질문 구성·생성:** 질문 10개 구성, 이력서 근거, 질문 품질 및 AI 생성 실패 시 대체 질문
3. **AI 면접 진행:** 음성·자막·녹음·STT, 답변 제한 시간, 꼬리질문, 화면 제어 제한
4. **장애·화면 이탈·마감:** 네트워크 단절, 재접속, 탭 종료·새로고침, 이탈 횟수, 공고 마감
5. **코딩테스트:** 문제 제공, 제한 시간, 자동 저장·제출, 붙여넣기 및 실행 환경 격리
6. **채점·1차 합격 결정:** 루브릭, 근거 문장, 점수 산식, 비정상 AI 출력, 관리자 권한
7. **결과 공개·데이터 삭제:** 공개 시각, 지원자 노출 범위, 녹화·면접 데이터 삭제

### 집중 관리 항목

| ID | 검증 항목 |
| --- | --- |
| TEST-01 | GPU 메모리 사용량과 동시 면접 처리 |
| TEST-02 | AI 채점 완료 시간 |
| TEST-03 | 장애 중단과 자발적 종료의 구분 |
| TEST-04 | 실제 답변에 근거하지 않은 채점의 차단 |
| TEST-05 | 음성 인식 정확도 |
| TEST-06 | 결과 공개 이전 정보 노출 방지 |

### 테스트 환경

- **실행:** Docker Compose, 로컬 접속(`127.0.0.1`)
- **프론트엔드:** Next.js 16, React 19, Monaco Editor
- **백엔드:** FastAPI, LangGraph, Celery
- **AI:** Qwen3-4B, Qwen3-8B, Whisper Large V3 Turbo, Supertonic(후보), PaddleOCR
- **저장소·인프라:** PostgreSQL 16, pgvector, Redis 7, MinIO
- **도구:** pytest, Playwright, freezegun, 모의 AI 응답
- **브라우저:** Chrome·Edge 데스크톱, 카메라·마이크·스피커 사용

성능 및 메모리의 최종 합격 판정은 계획서에 정의한 **기준 PC**에서 수행합니다. 개발 PC의 결과는 기능 점검 및 참고 자료로 구분합니다.

## 4. 테스트 케이스 (v0.2)

테스트 케이스는 **총 115개(TC-001~TC-115)**로 구성되어 있으며, `1depth(영역) → 2depth(화면) → 3depth(기능)` 체계로 화면·기능별 항목을 분류합니다.

주요 기록 항목은 다음과 같습니다.

| 항목 | 설명 |
| --- | --- |
| TC ID | 테스트 케이스 식별자 |
| 메뉴(1·2·3depth) | 대상 영역·화면·기능 |
| 테스트 | 검증할 동작 또는 조건 |
| 관련 완성 기준 | 연결되는 인수 기준(AC) |
| 입력값 | 테스트를 수행할 조건·입력 |
| 예상 결과값 | 정상 동작 시 기대하는 결과 |
| 실제 결과값 | 테스트 수행 후 확인한 결과 |
| 이슈 | 실패·차이·추가 확인 사항 |

**작성 원칙:** 예상 결과값은 사전에 정의하고, 실제 결과값과 이슈는 테스트 실행 후 기록합니다. UI 요소가 *존재하지 않아야 한다*는 요구사항도 유효한 테스트 대상입니다. 예를 들어 `TC-050`은 면접 화면의 중단·일시정지·건너뛰기 버튼 부재를 확인합니다.

## 5. 두 문서의 연결 관계

```text
PRD 완성 기준(AC-01~AC-23)
          │
          ▼
테스트 계획서 v0.1
(환경·범위·시나리오·집중 관리 기준)
          │
          ▼
테스트 케이스 v0.2
(TC-001~TC-115: 입력·예상 결과·실제 결과)
          │
          ▼
테스트 실행 → 이슈 기록 → 수정 → 재검증
```

테스트 계획서의 집중 관리 항목은 테스트 케이스의 `TC-109~TC-114`에 대응합니다. `TC-115`의 다음 질문 표시 시간 검증 기준도 계획서의 성능 기준과 함께 관리할 필요가 있습니다.

## 6. 문서 정합성 및 보완 사항

다음 항목은 **검토 및 보완 대상**이며, 문서 간 최종 합의가 완료되었다는 의미는 아닙니다.

- **기준 문서 버전:** 계획서는 PRD v1.6·TRD v1.5·화면정의서 v0.4를, 케이스는 테스트 계획서 v0.1·화면정의서 v0.4·API 명세서 v1.1을 표기합니다. 최신 승인본 기준으로 명시 범위를 정리합니다.
- **AC-08 검증 범위:** 계획서는 중단·일시정지 버튼 부재를, 케이스는 건너뛰기 버튼까지 확인합니다. 최종 정책을 확인하여 표현을 통일합니다.
- **장애·종료 판정:** 네트워크 장애와 창 닫기·새로고침을 구분하는 기준 및 서버 측 판정 가능성을 검토합니다.
- **성능 기준:** `TC-115`의 다음 질문 표시 시간 목표가 계획서의 검증 기준에도 반영되어야 하는지 확인합니다.
- **추적성과 실행 이력:** AC 연결이 없는 테스트, 실행 일시·담당자·Pass/Fail·결함 번호 기록 방식 등을 보완합니다.

## 7. 테스트 수행 및 문서 관리 원칙

1. 테스트 전에 적용 빌드와 기준 문서 버전, 실행 환경을 확인합니다.
2. 테스트 케이스의 입력값·예상 결과를 기준으로 기능을 실행합니다.
3. 실제 결과와 이슈를 기록하고, 예상 결과와 다르면 재현 조건을 남깁니다.
4. 수정 후 동일 조건에서 재검증합니다.
5. 요구사항 또는 정책이 변경되면 계획서와 케이스를 **함께 검토**하고 버전을 갱신합니다.
6. 공통 기획·설계 문서를 바탕으로 팀원별 구현 방식이 다를 수 있으므로, 구현 차이와 요구사항 위반을 구분하여 판단합니다.
