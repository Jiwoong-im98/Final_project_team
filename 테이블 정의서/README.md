## 2. 문서 개요 및 목적

본 문서는 AI 기반 1차 채용면접 자동화 플랫폼에서 사용하는 **25개 주요 데이터베이스 테이블**의 역할과 관계를 정의합니다. 회원 및 이력서, 채용공고, 지원, AI 면접, 코딩테스트, 평가 결과, 관리자 운영 데이터의 저장 구조를 설계하며, 각 컬럼의 자료형·PK·FK·UQ·NULL 허용 여부·기본값을 기술합니다.

주요 목적은 다음과 같습니다.

- 서비스의 데이터 구조와 참조 관계를 명확히 하고 데이터 무결성을 확보합니다.
- API 명세서 v1.1의 필드 및 상태값과 DB 스키마를 일치시킵니다.
- AI 질문 생성·답변·평가, 이력서 OCR, 실시간 면접 이벤트를 일관되게 기록합니다.
- 개인정보 암호화, 동의 증적 보관, 파일 삭제 및 감사 기록의 기준을 마련합니다.
- Alembic 마이그레이션과 개별 구현 시 공통 참고 기준으로 사용합니다.

## 3. 주요 기술 및 공통 규칙

| 항목 | 기준 |
|---|---|
| 관계형 DB | PostgreSQL 16 |
| 벡터 검색 | pgvector, BGE-M3 1,024차원 임베딩, HNSW 인덱스 |
| 스키마 변경 | Alembic으로만 관리 |
| 식별자 | 대부분 UUID (`gen_random_uuid()`), 누적 로그는 BIGSERIAL |
| 날짜·시간 | `timestamptz` 저장, 화면 및 예약 작업은 `Asia/Seoul` 기준 |
| 계산 점수 | `numeric(5,2)` 저장, API 응답에서는 문자열로 전달 |
| 구조화 데이터 | `jsonb` |
| 개인정보 암호화 | `_enc` 컬럼은 AES-256-GCM으로 암호화한 `bytea` |
| 비밀번호 | Argon2id 해시 |
| 무결성 | PK·FK·UQ·CHECK 제약조건 및 필요한 인덱스 |
| 외부 파일 | MinIO 파일 키 참조 |
| 임시 상태 | Redis |
| AI 실행 상태 | LangGraph 체크포인트 테이블은 프레임워크가 직접 관리 |

**상태값 관리:** API 명세서의 영문 상태값과 DB 상태값을 철자까지 일치시키며, 변경 시 양쪽 문서를 함께 수정합니다.

**삭제·동의 규칙:** 지원 건 삭제 시 질문·답변·평가·결과·녹화 등 종속 데이터를 정리합니다. **`consents`는 삭제하지 않고** `application_id`, `user_id` 연결을 `ON DELETE SET NULL`로 해제하여 동의·철회 증적을 보존합니다. 삭제 작업은 `deletion_logs`에 기록합니다. 동의 기록의 보관 기간은 팀의 확정이 필요합니다.

**계정 탈퇴:** `users` 행은 즉시 삭제하며 동일 이메일로 재가입할 수 있도록 설계합니다.

**LangGraph:** `checkpoints`, `checkpoint_blobs`, `checkpoint_writes`는 주요 25개 테이블과 별도로 프레임워크가 생성·관리합니다. `thread_id`는 지원 건 ID를 사용하며 지원 건 삭제 시 체크포인트도 정리합니다.

## 5. 핵심 데이터 설계

### 5.1. 지원 건 중심 관계

`applications`는 지원 1건을 식별하는 중심 테이블입니다. `posting_id`, `applicant_id`, `criteria_id`로 공고·회원·평가 기준을 연결하며, `(posting_id, applicant_id)`에 UNIQUE 제약을 적용해 **공고별 1인 1회 지원**을 보장합니다.

- `attempt_status`: `drafting`, `ready`, `interviewing`, `coding`, `interrupted`, `completed`, `ended`, `ended_closed`, `cancelled`, `not_taken_closed`
- `analysis_status`: `pending`, `running`, `decided`, `needs_review`
- `result_status`: `undecided`, `pass`, `fail`
- `release_status`: `scheduled`, `delayed`, `released`, `purged`
- 동시 면접 자리 점유(`holds_seat`), 화면 이탈 횟수(`exit_count`), 결과 공개 시각(`release_at`), 삭제 예정 시각(`purge_at`) 등을 함께 관리합니다.

### 5.2. 이력서 등록·업로드·OCR

- `user_resumes`: 사용자가 마이페이지에 보관하는 이력서 1개를 암호화하여 저장합니다.
- `resume_uploads`: 업로드 목적(`application`/`profile`), 파일 키, 페이지 유형, 예상 처리 시간, 추출 방식, OCR 신뢰도 및 오류 원인을 기록합니다.
- OCR 처리 단계: `uploaded` → `checking` → `ocr` → `structuring` → `done` (실패·취소 시 `failed`/`cancelled`).
- `applications.resume_snapshot_enc`: 지원 시 확정한 이력서 사본을 암호화해 저장하고 확정 후 수정하지 않습니다.

### 5.3. 공고 수정과 평가 기준

`posting_revisions`는 게시 이후 변경된 필드별 이전·이후 값과 지원자에게 표시할 변경 요약을 저장합니다. `evaluation_criteria`는 공고별 평가 항목 가중치, 코딩 반영 비율, 합격 기준 및 루브릭 버전을 관리하며, **첫 응시가 시작되면 기준을 잠가 변경하지 않도록** 설계합니다.

### 5.4. 질문은행·실제 질문·답변

`questions`는 Excel 기반 질문, AI 생성 질문, 예비 질문을 저장하며 `vector(1024)` 임베딩과 HNSW 인덱스로 유사 질문 검색을 지원합니다. 실제 출제 질문은 `interview_questions`에 스냅샷으로 별도 저장하고, 기본 질문과 꼬리질문을 연결합니다.

`answers`는 질문 하나에 답변 하나를 연결합니다. 중간 이탈로 음성이 나뉘어도 하나의 답변으로 관리하며, 음성 파일 키·최종 STT 텍스트·재시도 횟수를 저장합니다.

### 5.5. AI 평가와 코딩테스트

- `item_scores`: 5개 평가 항목(`expertise`, `logic`, `relevance`, `delivery`, `culture_fit`)별 **0~5점**, 근거 문장, 근거 검증 여부, 재생성 여부 기록.
- `results`: 면접·코딩·총점, AI 합격·불합격 판정, 판정 이유·근거, 검증 상태, 모델·프롬프트·루브릭 버전 및 지원자 공개용 `public_view` 저장. **확정 후 수정 불가**.
- `coding_problems`: 비공개 테스트를 암호화하며 API 응답이나 AI 입력에 포함하지 않습니다.
- `coding_submissions`: 문제별 마지막 저장 코드, 30초 간격 자동 저장 시각, 제출·채점 정보, 붙여넣기 차단 횟수 기록.

### 5.6. 실시간 면접·녹화·운영

- `session_events`: 연결 끊김, 화면 이탈, 종료 신호, STT 실패와 원인·발생 단계·판정·시간 기록.
- `recordings`: 최초 접속과 이어가기 구간별 파일, 마지막 업로드 조각 번호, 만료 시각 기록.
- `highlights`: 답변 음성의 재생 시작·종료 위치와 평가 근거 기록.
- `audit_logs`: 작업 주체·유형·대상·시각을 남기되 상세 열람 내용은 저장하지 않습니다.
- `app_settings` / `app_setting_history`: 운영 설정과 변경 이력 분리.

## 6. ERD 및 주요 관계

원본 PDF **2쪽**에 전체 ERD가 있으며, **3쪽**부터 25개 테이블의 목록과 상세 정의가 이어집니다.

- 회원 1명 → 여러 지원 건(`users` → `applications`)
- 채용공고 1건 → 여러 지원 건(`job_postings` → `applications`)
- 채용공고 1건 → 여러 공고 수정 기록 및 평가 기준 버전
- 지원 1건 → 여러 실제 면접 질문·녹화 구간·이벤트·코딩 제출
- 실제 면접 질문 1개 → 최대 1개 답변(`answers.interview_question_id` UNIQUE)
- 지원 1건 → 최대 1개 최종 결과(`results.application_id` UNIQUE)
- 지원·회원 삭제 → 동의 기록은 연결 해제 후 보존

관계도는 주요 키를 요약한 그림이므로, 실제 구현 시 **원본 PDF의 테이블별 상세 컬럼과 제약조건**을 우선 확인해야 합니다.

## 7. 데이터 보안·보관·삭제

| 대상 | 원본 문서의 처리 기준 |
|---|---|
| 비밀번호 | Argon2id 해시 |
| 이력서·전화번호 등 `_enc` 데이터 | AES-256-GCM 암호화 |
| 원본 이력서·음성·녹화 | MinIO 파일 키 참조 |
| 면접 녹화 | 응시 종료 후 **3일**, 만료 후 삭제 |
| 답변 음성·지원 데이터 | 결과 공개 후 **7일**을 기준으로 삭제 |
| 동의·철회 기록 | 지원·회원 삭제 후에도 보존, **보관 기간은 팀 확정 필요** |
| 삭제 작업 | `deletion_logs`에 삭제 범위·건수·시각 등 최소 기록 |
| 비공개 코딩 테스트 | 암호화 저장, API 및 AI 입력에서 제외 |

삭제 시 DB 행뿐 아니라 연계된 **MinIO 파일, Redis 키, LangGraph 체크포인트**의 정리도 고려합니다. 실제 보관·삭제 구현은 개인정보 처리방침 및 관련 문서와 일치하는지 검토해야 합니다.
