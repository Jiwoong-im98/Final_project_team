## 2. 문서 개요

본 문서는 **AI 기반 1차 채용면접 자동화 플랫폼의 데이터베이스 구조를 정의한 설계 문서**입니다.

TRD v1.5를 기준으로 서비스에서 사용하는 주요 데이터의 저장 방식과 테이블 간 관계를 정리하였으며, 각 테이블의 컬럼명, 자료형, 기본키(PK), 외래키(FK), 고유 제약조건(UQ), NULL 허용 여부 및 기본값을 명시하였습니다.

총 **20개의 주요 테이블**을 정의하고, 테이블 관계도(ERD)를 통해 회원, 채용공고, 지원, AI 면접, 코딩테스트, 평가 결과 및 관리자 기능 간의 데이터 연결 구조를 확인할 수 있도록 구성하였습니다.

또한 개인정보 암호화, 데이터 무결성, 삭제 정책, 로그 관리 및 벡터 검색과 관련된 설계 기준을 포함하였습니다.

본 문서는 향후 데이터베이스 구축, 백엔드 API 구현 및 데이터 관리 기능 개발 시 참고하는 **공통 데이터베이스 설계 기준 문서**입니다.

## 3. 작성 목적

- **데이터베이스 구조 명확화:** 서비스에서 사용하는 테이블과 컬럼의 역할 정의
- **테이블 관계 정리:** PK·FK를 이용한 데이터 간 연결 구조 및 참조 관계 정의
- **데이터 무결성 확보:** 고유 제약조건, NULL 조건, 기본값 및 상태값 검증 기준 수립
- **API 연계 기준 마련:** 백엔드에서 사용하는 데이터 저장·조회 구조 명확화
- **AI 면접 데이터 관리:** 질문, 답변, 채점 결과 및 실시간 이벤트 저장 구조 설계
- **개인정보 및 보안 관리:** 암호화 대상, 접근 기록 및 데이터 삭제 정책 정의
- **개발 환경 통일:** PostgreSQL과 Alembic을 이용한 스키마 관리 기준 마련

## 4. 주요 기술 및 데이터베이스 설계 기준

| 구분 | 설계 기준 |
|---|---|
| 관계형 데이터베이스 | PostgreSQL 16 |
| 벡터 검색 확장 | pgvector |
| 스키마 변경 관리 | Alembic |
| 주요 식별자 | UUID |
| 로그 식별자 | BIGSERIAL |
| 날짜 및 시각 | `timestamptz` |
| 점수 데이터 | `numeric(5,2)` |
| 구조화 데이터 | `jsonb` |
| 개인정보 암호화 | AES-256-GCM |
| 비밀번호 저장 | Argon2id 해시 |
| 관계 무결성 | PK, FK, UQ 및 CHECK 제약조건 |
| 데이터 삭제 | ON DELETE CASCADE 및 별도 삭제 기록 |
| AI 상태 관리 | LangGraph 체크포인트 테이블 |

### 4.1. 공통 데이터 설계 규칙

**1. 식별자 관리**

대부분의 테이블은 UUID를 기본키로 사용하며, 기록이 지속적으로 누적되는 로그 테이블에는 BIGSERIAL을 적용합니다.

**2. 날짜 및 시간 관리**

날짜와 시간은 `timestamptz`로 저장하고, 사용자 화면 및 예약된 작업의 시간 계산에는 한국 표준시(`Asia/Seoul`)를 적용합니다.

**3. 점수 데이터 관리**

평가 점수는 `numeric(5,2)` 자료형으로 저장하여 소수점 계산 오차를 줄입니다.

**4. 개인정보 보호**

컬럼명이 `_enc`로 끝나는 항목은 서버에서 AES-256-GCM으로 암호화한 후 `bytea` 형식으로 저장합니다.

**5. 상태값 검증**

응시 상태 및 분석 상태와 같이 허용값이 정해진 컬럼은 CHECK 제약조건을 적용합니다.

**6. 데이터 삭제 정책**

지원 데이터 삭제 시 연결된 동의, 질문, 답변, 점수, 결과 및 이벤트 기록도 함께 삭제하도록 설계하였습니다.

삭제 작업에 대한 최소한의 이력은 `deletion_logs`에 별도로 기록합니다.

**7. LangGraph 체크포인트 관리**

LangGraph에서 사용하는 `checkpoints`, `checkpoint_blobs`, `checkpoint_writes` 테이블은 프레임워크가 직접 생성하고 관리합니다.

해당 체크포인트는 지원 건의 ID를 기준으로 연결하며, 관련 지원 데이터 삭제 시 함께 제거합니다.

## 6. 핵심 데이터 구조 및 설계 특징

### 6.1. 지원 데이터 중심 구조

`applications` 테이블은 지원자 한 명이 특정 채용공고에 지원한 내용을 관리하는 중심 테이블입니다.

해당 테이블을 기준으로 동의 정보, 면접 질문, 코딩테스트 제출 내역, 평가 결과 및 면접 이벤트가 연결됩니다.

- 하나의 채용공고에 동일 지원자는 한 번만 지원할 수 있도록 고유 제약조건 적용
- 지원 당시 사용한 평가 기준 연결
- 이력서 원본 위치 및 암호화된 이력서 사본 저장
- 응시 상태, 분석 상태 및 결과 공개 상태 관리
- 동시 면접 자리 점유 및 해제 상태 기록
- 결과 공개 시각과 데이터 삭제 예정 시각 관리

### 6.2. 질문은행 및 벡터 검색

`questions` 테이블은 기존 Excel 질문, AI 생성 질문 및 예비 질문을 통합 관리합니다.

- 질문 출처 및 종류 구분
- 질문 본문과 답변 제한 시간 관리
- 평가 항목 및 중복 질문 그룹 기록
- BGE-M3 기반 1,024차원 임베딩 저장
- pgvector의 HNSW 인덱스를 활용한 유사 질문 검색

실제 면접에서 사용한 질문은 `interview_questions`에 별도로 저장하여 질문은행의 원본 데이터와 구분합니다.

### 6.3. AI 면접 답변 및 평가 데이터

`answers` 테이블은 질문별 음성 파일 위치와 최종 STT 변환 결과를 저장합니다.

화면 이탈 이후 이어서 답변한 경우에도 동일 질문에 대한 답변을 하나의 데이터로 관리하도록 설계하였습니다.

`item_scores` 테이블은 AI가 평가한 항목별 점수와 근거 문장을 기록합니다.

- 평가 항목별 0~5점 점수
- 평가 근거 문장
- 근거 문장의 실제 답변 포함 여부
- 근거 오류로 인한 재생성 여부

`results` 테이블은 면접 점수, 코딩테스트 점수, 최종 점수 및 AI 판정 결과를 저장합니다.

또한 평가에 사용한 모델, 프롬프트 및 루브릭 버전을 기록하여 평가 결과의 생성 기준을 확인할 수 있도록 합니다.

### 6.4. 코딩테스트 데이터 관리

`coding_problems`와 `coding_submissions`를 통해 코딩테스트 문제와 제출 결과를 구분하여 관리합니다.

- 공개 테스트 및 암호화된 비공개 테스트 구분
- 실행 시간과 메모리 제한 저장
- 마지막 자동 저장 코드 관리
- 최종 제출 시각 및 채점 결과 기록
- 외부 코드 붙여넣기 시도 횟수 기록

비공개 테스트 데이터는 암호화하여 저장하고, API 및 AI 입력에 포함하지 않는 것을 원칙으로 합니다.

### 6.5. 장애 및 화면 이탈 기록

`session_events` 테이블은 면접 진행 중 발생하는 연결 장애와 화면 이탈 이벤트를 저장합니다.

주요 기록 항목은 다음과 같습니다.

- Heartbeat 누락
- 네트워크 연결 종료
- 장치 오류
- 서버 오류
- 브라우저 종료
- 화면 가시성 및 포커스 변경
- 전체 화면 해제
- 장애 또는 이탈 여부 판단 결과

이를 통해 응시 중 발생한 이벤트의 종류와 발생 시각을 확인하고, 장애 복구 및 응시 종료 판단에 활용할 수 있도록 합니다.

### 6.6. 관리자 및 시스템 운영

관리자 기능과 관련하여 내부 메모, 알림, 감사 로그 및 운영 설정값을 별도 테이블로 구분하였습니다.

특히 `audit_logs`에는 주요 작업의 실행 주체와 대상, 발생 시각을 기록하되, 작업 대상의 상세 내용 자체는 저장하지 않도록 설계하였습니다.

`app_settings`는 동시 면접 상한과 같은 운영 설정을 관리하며, 서버 재시작 없이 변경 가능한 설정값을 저장합니다.

## 7. ERD 및 데이터 관계

본 문서에는 주요 테이블 간 관계를 확인할 수 있도록 ERD가 포함되어 있습니다.

ERD에서는 기본키와 외래키를 중심으로 다음 관계를 표현합니다.

- 회원과 지원 내역
- 채용공고와 평가 기준
- 지원 내역과 면접 질문
- 질문은행과 실제 출제 질문
- 면접 질문과 답변 및 평가 점수
- 지원 내역과 코딩테스트 제출 결과
- 지원 내역과 최종 평가 결과
- 지원 내역과 장애 이벤트 및 관리자 메모

**주요 관계 특징**

- 하나의 회원은 여러 채용공고에 지원할 수 있습니다.
- 하나의 채용공고에는 여러 지원 내역이 연결될 수 있습니다.
- 하나의 지원 건에는 여러 면접 질문과 코딩테스트 제출 내역이 연결됩니다.
- 하나의 면접 질문에는 최대 하나의 답변이 연결됩니다.
- 하나의 지원 건에는 최대 하나의 최종 결과가 연결됩니다.
- 평가 기준은 버전별로 구분하여 관리합니다.

ERD는 데이터 구조의 전체 관계를 확인하기 위한 자료이며, 실제 컬럼과 제약조건은 테이블별 상세 정의를 기준으로 합니다.

## 8. 데이터 보안 및 보관 정책

### 8.1. 개인정보 암호화

전화번호와 이력서 사본 등 암호화 대상 데이터는 AES-256-GCM으로 암호화하여 저장하도록 설계하였습니다.

비밀번호는 원문을 저장하지 않고 Argon2id 해시를 사용합니다.

### 8.2. 파일 저장 관리

이력서 원본, 면접 답변 음성 및 녹화 파일은 데이터베이스에 직접 저장하는 대신 MinIO 저장 위치를 참조하는 방식으로 관리합니다.

### 8.3. 데이터 삭제 및 보관

지원 건 삭제 시 관련 데이터를 연쇄 삭제하며, 삭제 이력은 별도 로그로 관리합니다.

- 면접 녹화: 응시 종료 후 3일 보관
- 지원 및 평가 데이터: 결과 공개 후 7일 보관 기준
- 삭제 기록: 삭제 대상의 상세 내용이 아닌 작업 결과 중심으로 저장

### 8.4. 감사 로그

관리자의 결과 조회, 녹화 재생, 메모 작성, 평가 기준 및 운영 설정 변경 등의 작업을 감사 로그로 관리합니다.

| 관련 문서 | 연계 내용 |
|---|---|
| PRD | 제품 요구사항과 데이터 관리 기능의 일치 여부 확인 |
| TRD | 데이터베이스 기술 및 저장·보안 정책 확인 |
| 화면정의서 | 화면에서 사용하는 데이터와 상태값 확인 |
| API 명세서 | 요청·응답 필드와 실제 데이터베이스 컬럼 연결 |
| ERD | 테이블 간 관계 및 참조 구조 확인 |
| 기술 아키텍처 | 서버, DB, MinIO, Redis 및 AI 처리 구성 간 연결 확인 |
| AI 아키텍처 | 질문 생성, RAG, STT 및 평가 결과의 데이터 저장·조회 구조 연계 |

본 문서는 데이터베이스 구축 및 백엔드 구현을 위한 기준으로 활용하되, API 명세서와 화면정의서의 변경 사항이 발생할 경우 관련 테이블 구조에도 반영이 필요한지 검토합니다.

현재 테이블 정의서는 초기 설계 단계의 데이터 구조를 정리한 문서이며, 후속 개발 과정에서 다음 사항을 검토할 예정입니다.

2. 화면정의서의 응시 상태 및 분석 상태와 데이터베이스 상태값 비교

4. 데이터 보관 및 삭제 정책의 구현 가능성 확인

8. AI 아키텍처 작성 이후 추가 데이터 저장 요구사항 검토
