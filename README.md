# AI 면접 프로젝트

## 1. 프로젝트 개요

본 프로젝트는 AI 기반 1차 채용면접 자동화 플랫폼을 기획하고 구현하는 것을 목표로 합니다.

지원자의 채용공고 확인 및 지원부터 AI 면접, 코딩테스트, 자동 평가, 결과 확인까지의 과정을 하나의 서비스로 구성하고, AI 기술을 활용하여 면접 진행과 평가 업무를 지원하는 시스템을 개발하고자 합니다.

현재 프로젝트는 **공통 기획 및 설계 문서의 주요 작성 작업을 마무리하고, 기술 명세 보완과 프로그램 구현을 준비하는 단계**에 있습니다.

프로젝트의 전체적인 방향을 공유하고, 팀원 간 기능과 기술에 대한 이해도를 높이기 위해 공통 문서를 작성하였으며, 이후 각 팀원은 해당 문서를 참고하여 개별적인 프로그램 구현을 진행할 예정입니다.

### 1.1. 프로젝트 진행 원칙

- **문서 작성:** 팀원 간 논의를 통해 공통으로 진행합니다.
- **프로그램 구현:** 공통 문서를 참고하여 각 팀원이 개별적으로 구현을 시도합니다.
- **구현 방식:** 개인별 기술 선택과 구현 방식은 서로 다를 수 있습니다.
- **문서 활용:** 공통 문서는 개발을 위한 기준 및 참고 자료로 활용합니다.
- **피드백 반영:** 팀원들의 의견을 피드백노트에 기록하고, 검토를 거쳐 공통 문서에 반영합니다.
- **버전 관리:** 문서의 수정 및 변경 사항은 GitHub를 통해 관리하며, 주요 변경 내용은 README와 관련 문서에 기록합니다.

※ 공통 문서 작성이 반드시 동일한 코드나 단일 프로그램의 공동 개발을 의미하는 것은 아닙니다.

### 1.2. 프로젝트 주요 기능

| 구분 | 주요 기능 |
|---|---|
| 회원 및 인증 관리 | 지원자 회원가입, 로그인, 비밀번호 관리, 관리자 인증 및 접근 권한 관리 |
| 채용공고 관리 | 공고 등록·수정·마감, AI 공고 초안 생성, 평가 기준 설정 |

| 코딩테스트 | 코딩 문제 출제, 코드 작성 및 저장, 테스트케이스 기반 채점 |

세부 기능과 구현 기준은 PRD, TRD, 기능정의서, 화면정의서 및 기타 설계 문서를 참고합니다.

#### 9. ERD — 데이터베이스 관계 설계

**작성 완료 / GitHub 업로드 예정**

ERD는 서비스에서 사용하는 데이터베이스 테이블 간의 관계를 정의한 문서입니다.

주요 작성 내용은 다음과 같습니다.

- 회원, 채용공고, 지원, 면접, 평가 및 관리자 기능 간 데이터 관계 설계
- 기본키(PK)와 외래키(FK)를 이용한 참조 구조 정의
- 지원 건을 중심으로 연결되는 면접·평가·코딩테스트 데이터 관계 정리
- 테이블 간 1:1 및 1:N 관계 표현
- 데이터 무결성과 중복 방지를 위한 관계 구조 검토

ERD는 테이블 정의서와 함께 데이터베이스 구현 및 백엔드 API 개발을 위한 참고 자료로 활용할 예정입니다.

#### 10. 테이블 정의서 — 데이터베이스 상세 설계

**작성일: 2026년 10월 29일**

**작성 완료 / GitHub 업로드 예정**

테이블 정의서는 TRD v1.5를 기준으로 서비스에서 사용하는 데이터베이스의 상세 구조를 정리한 문서입니다.

PostgreSQL 16과 pgvector를 기준으로 **총 20개의 주요 테이블**을 정의하였으며, 각 테이블의 컬럼명, 자료형, 기본값, PK·FK·UQ 제약조건 및 NULL 허용 여부를 명시하였습니다.

**주요 테이블 구성**

| 영역 | 주요 테이블 |
|---|---|
| 회원 및 인증 | `users`, `consents` |
| 채용공고 및 평가 기준 | `job_codes`, `job_postings`, `evaluation_criteria` |
| 지원 및 면접 | `applications`, `questions`, `interview_questions`, `answers` |
| 평가 및 결과 | `item_scores`, `results`, `highlights` |
| 코딩테스트 | `coding_problems`, `coding_submissions` |
| 면접 이벤트 | `session_events` |
| 관리자 및 운영 | `memos`, `notifications`, `audit_logs`, `deletion_logs`, `app_settings` |

**주요 설계 기준**

- PostgreSQL 16 및 pgvector 사용
- Alembic 기반 데이터베이스 스키마 변경 관리
- UUID 기반 주요 데이터 식별
- `timestamptz` 기반 날짜·시간 저장
- `numeric(5,2)` 기반 평가 점수 저장
- AES-256-GCM 기반 개인정보 암호화
- Argon2id 기반 비밀번호 해시
- CHECK 및 UNIQUE 제약조건을 통한 데이터 무결성 관리
- 지원 데이터 삭제 시 관련 데이터 연쇄 삭제
- LangGraph 체크포인트 테이블 별도 관리

**AI 관련 데이터 설계**

질문은행에는 기존 질문과 AI 생성 질문을 저장하며, BGE-M3 임베딩과 pgvector의 HNSW 인덱스를 이용한 유사 질문 검색 구조를 포함합니다.

실제 면접 질문, 음성 답변, STT 변환 결과 및 평가 점수는 별도 테이블에 저장하도록 설계하였습니다.

AI 평가 결과에는 점수와 판정뿐 아니라 평가 근거, 모델 버전, 프롬프트 버전 및 루브릭 버전을 기록합니다.

**데이터 보관 및 삭제 정책**

- 면접 녹화: 응시 종료 후 3일 보관
- 지원 및 평가 데이터: 결과 공개 후 7일 보관 기준
- 이력서 및 미디어 파일: MinIO 저장 위치 참조
- 데이터 삭제 이력: `deletion_logs`에 별도 기록

현재 테이블 정의서는 작성 완료 상태이며, GitHub 업로드 이후 문서 위치와 후속 변경 사항을 추가할 예정입니다.

#### 11. AI 아키텍처 — 작성 예정

AI 아키텍처는 AI 관련 기능의 모델 구성과 데이터 처리 흐름을 구체화하기 위한 문서로 작성할 예정입니다.

### 2.4. 문서 간 정합성 검토 사항

현재 주요 설계 문서의 작성과 개정이 진행되면서 일부 기능 및 데이터 처리 정책에서 차이가 확인되었습니다.

실제 구현 과정에서 오류가 발생하지 않도록 다음 항목을 우선적으로 검토할 예정입니다.

| 검토 항목 | 확인 내용 |
|---|---|
| 응시 상태값 | API와 테이블 정의서의 `interrupted` / `suspended` 차이 |
| 분석 상태값 | API와 테이블 정의서의 `decided` / `done` 차이 |
| 결과 공개 상태 | API와 테이블 정의서의 `scheduled`, `delayed`, `hidden` 사용 기준 |
| 지원서 작성 상태 | `drafting` 상태의 데이터베이스 반영 여부 |
| 공고 수정 이력 | API에서 사용하는 `posting_revisions` 테이블 정의 필요 여부 |
| 공고 생성 출처 | `ai_draft` 등 추가 출처값의 저장 기준 |
| AI 판정 검증 | API 명세서와 최신 화면정의서 간 검증 방식 차이 |
| STT 최종 실패 | 동일 질문 재시도 또는 장애 중단·재접속 처리 방식 |
| API 수량 | 추가된 미디어 API의 REST API 총수 포함 여부 |

위 항목은 **현재 검토가 필요한 사항**이며, 최종 정책이 확정된 것은 아닙니다.

검토 결과에 따라 PRD, TRD, 화면정의서, API 명세서 및 테이블 정의서를 함께 수정하여 문서 간 일관성을 유지할 예정입니다.

## 3. 문서 관리 및 업무 현황

본 프로젝트는 공통 문서의 체계적인 관리와 팀원 간 업무 현황 공유를 위해 **파일관리대장, WBS 업무관리, 회의록, 피드백노트**를 운영합니다.

각 문서는 서로 다른 목적을 가지고 있으며, 프로젝트 진행 과정에서 발생하는 정보의 누락을 방지하고 업무의 연속성을 확보하기 위해 활용합니다.

### 3.1. 파일관리대장 (Document Register)

**목적: 프로젝트에서 작성한 문서의 현황을 체계적으로 관리하고, 필요한 문서를 쉽게 확인하기 위함입니다.**

파일관리대장은 현재 프로젝트에서 작성되었거나 작성 중인 문서들을 관리하기 위한 자료입니다.

각 문서는 성격과 목적에 따라 디렉토리별로 구분하여 정리하였으며, 팀원들이 필요한 문서를 쉽게 찾아 확인할 수 있도록 구성하였습니다.

또한 문서별 담당 역할과 마감기한을 지정하여 작성 책임과 작업 일정을 명확하게 관리합니다.

**주요 활용 내용**

- 현재 존재하는 문서의 목록 및 관리 현황 확인
- 문서의 종류와 목적에 따른 디렉토리별 분류
- 각 문서의 저장 위치 및 접근 경로 확인
- 문서별 담당 역할 및 마감기한 관리
- 문서의 작성 및 수정 상태 확인
- 중복 작성이나 문서 누락 방지

### 3.2. WBS 업무관리 (Work Breakdown Structure)

**목적: 프로젝트의 실제 업무 진행 상황을 지속적으로 관리하고, 담당자별 작업 과정과 일정 지연 여부를 확인하기 위함입니다.**

WBS 업무관리는 프로젝트에서 진행하는 실무를 체계적으로 관리하기 위해 작성한 업무관리 시트입니다.

각 담당자가 수행해야 하는 작업을 구분하고, 업무별 진행 일정과 현재 상태를 확인할 수 있도록 구성하였습니다.

**주요 활용 내용**

- 팀원별 담당 업무 및 작업 범위 확인
- 업무별 예정 시작일과 마감일 관리
- 실제 시작일과 완료일 기록
- 현재 업무 진행 상태 및 지연 여부 확인
- 향후 진행해야 할 업무와 후속 작업 파악
- 최종 산출물까지의 세부 업무 구체화
- 프로젝트 전체 일정 및 진행 현황 공유

팀원들은 본인이 담당한 업무의 진행 상황을 지속적으로 갱신하며, 이를 통해 전체 프로젝트의 작업 현황을 공유합니다.

### 3.3. 회의록 (Meeting Minutes)

**목적: 지금까지 진행한 회의 내용을 기록하고, 논의 과정에서 누락되거나 부족했던 사항을 확인하여 보완하기 위함입니다.**

회의록은 프로젝트를 진행하면서 팀원들이 논의한 내용을 텍스트로 기록하고 관리하기 위한 문서입니다.

단순히 회의 결과만을 기록하는 것이 아니라, 논의 과정에서 제시된 의견과 결정 사항을 보존하여 이후 문서 작성과 개발 과정에서 참고할 수 있도록 합니다.

**주요 활용 내용**

- 지금까지 진행한 회의 내용 기록 및 보존
- 팀원별 주요 의견과 논의 사항 정리
- 회의를 통해 합의된 결정 사항 확인
- 누락되거나 추가 검토가 필요한 내용 파악
- 후속 회의에서 논의할 사항 도출
- PRD, TRD 및 기타 설계 문서 작성 시 참고 자료로 활용

### 3.4. 피드백노트 (Feedback Notes)

**목적: 프로젝트 문서에 대한 팀원들의 피드백을 한곳에 모아 관리하고, 문서의 완성도와 정확성을 높이기 위함입니다.**

피드백노트는 팀원들이 작성된 문서를 검토하면서 발견한 문제점, 개선 의견, 추가 요청 사항 등을 기록하는 공간입니다.

공통 문서 작성 과정에서는 팀원마다 기능과 기술에 대한 이해나 관점이 다를 수 있으므로, 각자의 의견을 체계적으로 수집하고 검토하는 과정이 필요합니다.

**주요 활용 내용**

- 작성된 문서에 대한 팀원별 피드백 수집
- 문서의 오류, 누락 및 불명확한 내용 기록
- 기능 및 기술 설계에 대한 개선 의견 정리
- 추가 검토나 논의가 필요한 사항 관리
- 피드백 반영 여부 및 수정 사항 확인
- 문서 업데이트 시 기존 의견 참고

피드백노트는 **문서 검토 → 피드백 기록 → 수정 여부 논의 → 문서 보완**으로 이어지는 개선 과정에 활용합니다.

### 3.5. 문서별 역할 구분

| 구분 | 핵심 목적 | 주요 확인 사항 |
|---|---|---|
| 파일관리대장 | 문서 및 담당 역할 관리 | 어떤 문서가 존재하며, 누가 언제까지 작성하는가? |
| WBS 업무관리 | 업무 및 일정 관리 | 누가 어떤 업무를 맡았으며, 현재 어디까지 진행했는가? |
| 회의록 | 논의 내용 관리 | 무엇을 논의하고 결정했으며, 어떤 사항을 보완해야 하는가? |
| 피드백노트 | 문서 검토 및 개선 관리 | 문서에 어떤 문제나 개선 의견이 있으며, 무엇을 수정해야 하는가? |

네 문서는 상호 보완적으로 활용됩니다.

회의록에서 결정된 작업은 필요한 경우 WBS 업무관리에 반영하고, 작업 결과로 작성되거나 수정된 문서는 파일관리대장을 통해 관리합니다.

이후 팀원들이 문서를 검토하면서 발견한 문제점과 개선 의견은 피드백노트에 기록하고, 검토 결과에 따라 문서를 보완합니다.

이를 통해 **논의 → 업무 수행 → 문서 작성 → 피드백 → 문서 개선 및 관리**로 이어지는 프로젝트 진행 과정을 체계적으로 확인할 수 있도록 합니다.

## 4. 향후 진행 방향

### 4.2. 프로그램 구현 단계 전환

구현 단계에서는 각 팀원이 공통 문서를 참고하여 개별적으로 프로그램 개발을 진행합니다.

주요 구현 대상은 다음과 같습니다.

1. 프런트엔드 화면 및 사용자 인터페이스
2. 백엔드 API 및 인증·권한 관리
3. 데이터베이스 구축 및 데이터 처리
4. AI 질문 생성과 면접 진행 기능
5. 음성 인식·합성 및 실시간 통신
6. 코딩테스트 및 자동 채점
7. AI 평가·판정 및 결과 리포트
