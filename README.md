# AI 면접 프로젝트

> **기준일:** 2026년 10월 29일  
> **진행 단계:** 공통 기획·설계 문서 주요 작성 완료 / 기술 명세 보완 및 개별 구현 준비

## 1. 프로젝트 개요

본 프로젝트는 **AI 기반 1차 채용면접 자동화 플랫폼**을 기획하고 구현하는 것을 목표로 합니다. 지원자의 채용공고 확인 및 지원부터 AI 면접, 코딩테스트, 자동 평가, 결과 확인까지의 과정을 하나의 서비스로 구성합니다.

공통 문서는 팀원 간 논의를 통해 작성하며, **프로그램은 각 팀원이 공통 문서를 참고해 개별적으로 구현**합니다. 기술 스택과 구현 방식은 개인별로 달라질 수 있습니다. 공통 문서 작성은 동일한 코드나 단일 프로그램의 공동 개발을 의미하지 않습니다.

### 1.1. 프로젝트 진행 원칙

- **문서 작성:** 팀원 간 논의를 통해 공통으로 진행합니다.
- **프로그램 구현:** 공통 문서를 참고하여 각 팀원이 개별적으로 구현합니다.
- **구현 방식:** 개인별 기술 선택과 구현 방식은 달라질 수 있습니다.
- **문서 활용:** 공통 문서는 개발 기준 및 참고 자료입니다.
- **피드백 반영:** 피드백노트에 의견을 기록하고 검토 후 문서에 반영합니다.
- **버전 관리:** GitHub에서 변경 사항을 관리하고 README 및 관련 문서에 주요 변경 내역을 기록합니다.

| 채용공고 관리 | 공고 등록·수정·마감, AI 공고 초안 생성, 평가 기준 설정 |

## 2. 현재 진행 상황

**기준일: 2026년 10월 29일**

PRD, TRD, 화면정의서, 서비스 플로우차트 등 주요 공통 문서를 개정하였으며, 기능정의서, 시나리오 기획서, 기술 아키텍처, API 명세서를 작성했습니다. **ERD와 테이블 정의서는 작성 완료되었으나 GitHub 업로드 예정**이며, AI 아키텍처는 작성 예정입니다. 구현 전 문서 간 기술·정책 정합성을 추가 검토합니다.

### 2.2. 주요 문서 업데이트 내역

#### PRD — 제품 요구사항 정의

- AI 기반 1차 채용면접의 기능 및 요구사항 구체화
- 지원자·관리자 역할과 접근 권한, 공고·이력서·면접·코딩테스트·평가 기능 정의
- 응시 상태, 결과 공개, 개인정보 처리 정책 보완
- 관련 설계 문서와 요구사항 정합성 검토

#### TRD — 기술 요구사항 정의 (v1.5)

- 개발 환경과 기술 스택, AI 모델 운영 환경 및 서버 자원 제약 구체화
- 프런트엔드·백엔드·AI 처리 연동, 실시간 통신 및 비동기 처리 기준
- AI 평가·판정, 장애 복구, 보안·데이터 보관·운영 정책 보완

#### 화면정의서 — 화면 설계 및 사용자 동작 (v0.5)

- PRD v1.6, TRD v1.5, 플로우차트 08v 반영
- 와이어프레임, 버튼 동작, 화면 전환 및 라우트 가드 정리
- AI 판정 검증, STT 최종 실패 시 장애 중단·재접속 처리 반영
- 동시 면접 상한, 화면 이탈, 응시 복구 정책 및 추가 API·데이터 필드 검토

#### 서비스 플로우차트 — 전체 서비스 흐름 (08v)

- 지원자·관리자 서비스 흐름, 공고 등록부터 결과 공개까지의 절차 구체화
- 질문 구성, 면접, 코딩테스트, 평가, AI 판정 검증 및 장애 처리 반영
- 화면 이탈, 재접속, 접수 마감 등 예외 흐름 보완
- GitHub 최초 등록 버전 05v 이후 개정 내용 관리

#### 기능정의서 — 세부 기능 명세 (v0.2)

- **13개 기능 영역, 129개 세부 기능** 정의
- 동작 조건, 처리 기준, 공통 규칙, 변경 이력 정리
- PRD·TRD·화면정의서 간 누락 및 정책 차이 검토

#### 시나리오 기획서 — 서비스 이용 시나리오

- 지원자·관리자·AI·시스템 관점의 정상 및 예외 시나리오 작성
- 공고 등록, 지원, 면접, 평가, 결과 확인과 네트워크 장애·화면 이탈·질문 생성 실패·평가 지연 반영
- 구현 및 테스트 단계에서 검증 시나리오로 활용

#### 기술 아키텍처 — 시스템 구성 설계 (v1.1)

- 프런트엔드, 백엔드, AI 처리, 데이터 저장 구조 및 서비스별 역할 정의
- REST API, WebSocket, WebRTC, 비동기 작업 연동 설계
- 모델 배치·서버 자원, 장애 복구, 보안, 배포 구조와 기술 위험 검토

#### API 명세서 — 시스템 인터페이스 정의 (v1.1)

Next.js와 FastAPI 간 데이터 통신 및 실시간 면접 연동 규격을 정의합니다. 문서상 **REST API 64개, 실시간 메시지 23종**이 명시되어 있습니다.

- 인증·공고·지원·면접·코딩테스트·관리자 API의 엔드포인트 및 요청·응답 정의
- WebSocket·WebRTC 실시간 면접 규격, 미디어 파일 제공 및 접근 권한 보완
- 게시 후 공고 수정 이력, 화면 이탈·STT 실패 메시지, `sendBeacon` 규칙 추가
- Next.js 프록시·로컬 접속 환경 검토, 확인 사항 A-01~A-19 관리
- 화면정의서 v0.4 등을 기준으로 작성되어 **최신 v0.5와 정책 차이 검토 필요**
- 추가 미디어 API의 총수 포함 여부 및 ERD·테이블 정의서 정합성 확인 예정

#### ERD — 데이터베이스 관계 설계 (작성 완료 / 업로드 예정)

- 회원·공고·지원·면접·평가·관리자 데이터 관계 정의
- PK·FK 참조, 지원 건 중심의 면접·평가·코딩테스트 관계, 1:1·1:N 관계 설계
- 데이터 무결성·중복 방지 구조 검토; DB 구현과 백엔드 API 개발에 활용

#### 테이블 정의서 — 데이터베이스 상세 설계 (2026-10-29 작성 / 업로드 예정)

**PostgreSQL 16 + pgvector** 기준으로 **20개 주요 테이블**의 컬럼, 자료형, 기본값, PK·FK·UQ, NULL 허용 여부를 정의했습니다.

| 영역 | 주요 테이블 |
|---|---|
| 회원 및 인증 | `users`, `consents` |
| 채용공고 및 평가 기준 | `job_codes`, `job_postings`, `evaluation_criteria` |
| 지원 및 면접 | `applications`, `questions`, `interview_questions`, `answers` |
| 평가 및 결과 | `item_scores`, `results`, `highlights` |
| 코딩테스트 | `coding_problems`, `coding_submissions` |
| 면접 이벤트 | `session_events` |
| 관리자 및 운영 | `memos`, `notifications`, `audit_logs`, `deletion_logs`, `app_settings` |

**주요 설계 기준**

- Alembic 스키마 변경 관리, UUID 식별자, `timestamptz` 날짜·시간, `numeric(5,2)` 평가 점수
- AES-256-GCM 개인정보 암호화, Argon2id 비밀번호 해시
- CHECK·UNIQUE 제약조건, 지원 데이터 삭제 시 관련 데이터 연쇄 삭제
- LangGraph 체크포인트 테이블 별도 관리
- 질문은행의 기존·AI 생성 질문 저장, BGE-M3 임베딩과 pgvector HNSW 유사 질문 검색
- 실제 면접 질문, 음성 답변, STT 결과, 평가 점수 분리 저장
- 평가 근거, 모델·프롬프트·루브릭 버전 기록
- 이력서·미디어 파일은 MinIO 저장 위치 참조

**설계상 데이터 보관 기준**

- 면접 녹화: 응시 종료 후 **3일**
- 지원 및 평가 데이터: 결과 공개 후 **7일**
- 삭제 이력: `deletion_logs` 별도 기록

> 보관·삭제 기간과 암호화·연쇄 삭제 정책은 구현 전 법적 요구사항 및 실제 서비스 운영 정책과의 적합성을 검토해야 합니다.

#### AI 아키텍처 — 작성 예정

AI 모델별 역할, LLM 질문 생성·평가, RAG·질문은행, STT·TTS, 실시간 처리 파이프라인, 백엔드 연동, 모델 실행 자원, AI 처리 실패·복구 방식을 검토할 예정입니다. 최종 구성과 기술 선택은 작성 및 검토 후 확정합니다.

### 2.4. 문서 간 정합성 검토 사항

| 검토 항목 | 확인할 내용 |
|---|---|
| 응시 상태값 | API `interrupted`와 테이블 정의서 `suspended` 차이 |
| 분석 상태값 | `decided`와 `done` 차이 |
| 결과 공개 상태 | `scheduled`, `delayed`, `hidden` 사용 기준 |
| 지원서 작성 상태 | `drafting`의 DB 반영 여부 |
| 공고 수정 이력 | `posting_revisions` 테이블 필요 여부 |
| 공고 생성 출처 | `ai_draft` 등 추가 출처값 저장 기준 |
| AI 판정 검증 | API와 최신 화면정의서의 검증 방식 차이 |
| STT 최종 실패 | 동일 질문 재시도 또는 장애 중단·재접속 정책 |
| API 수량 | 추가 미디어 API의 REST 총수 포함 여부 |

이 항목은 **검토 과제이며 확정 정책이 아닙니다.** 결정 후 PRD·TRD·화면정의서·API 명세서·테이블 정의서를 함께 갱신합니다.

## 3. 문서 관리 및 업무 현황

### 3.1. 파일관리대장 (Document Register)

프로젝트 문서의 **목록, 디렉토리별 분류, 저장 위치, 담당 역할, 마감기한, 작성·수정 상태**를 관리합니다. 문서 누락과 중복 작성을 방지하고 팀원들이 필요한 문서를 찾도록 지원합니다.

### 3.2. WBS 업무관리 (Work Breakdown Structure)

담당자별 업무 범위, 예정 시작·마감일, 실제 시작·완료일, 진행 상태와 지연 여부를 관리합니다. 팀원들은 작업 상태를 지속적으로 갱신하고 후속 작업 및 전체 일정을 공유합니다.

### 3.3. 회의록 (Meeting Minutes)

회의에서 제시된 의견, 합의된 결정, 누락·보완 사항, 후속 논의 주제를 기록합니다. PRD·TRD 등 설계 문서의 결정 근거로 활용합니다.

### 3.4. 피드백노트 (Feedback Notes)

문서의 오류·누락·불명확한 내용, 기능·기술 개선 의견, 추가 검토 사항과 반영 여부를 기록합니다. **문서 검토 → 피드백 기록 → 수정 여부 논의 → 문서 보완**의 흐름으로 운영합니다.

### 3.5. 문서별 역할 구분

| 문서 | 핵심 목적 | 확인 사항 |
|---|---|---|
| 파일관리대장 | 문서·담당 역할 관리 | 어떤 문서가 있고 누가 언제까지 작성하는가? |
| WBS 업무관리 | 업무·일정 관리 | 누가 어떤 작업을 맡았고 어디까지 진행했는가? |
| 회의록 | 논의·결정 관리 | 무엇을 논의·결정하고 무엇을 보완해야 하는가? |
| 피드백노트 | 검토·개선 관리 | 어떤 문제·개선 의견이 있으며 무엇을 수정해야 하는가? |

**논의 → 업무 수행 → 문서 작성 → 피드백 → 문서 개선 및 관리**로 연결합니다. 회의 결정은 필요시 WBS에 반영하고, 산출물은 파일관리대장에 등록하며, 검토 의견은 피드백노트로 관리합니다.

2. 백엔드 API와 인증·권한 관리
3. 데이터베이스 구축 및 데이터 처리
4. AI 질문 생성과 면접 진행
5. STT·TTS 및 실시간 통신
6. 코딩테스트와 자동 채점
7. AI 평가·판정과 결과 리포트

### 4.3. 문서 업데이트 및 버전 관리

GitHub에 문서를 순차 등록하고 다음 사항을 README에 반영합니다.

- 신규 문서의 작성·등록 여부 및 저장 위치
- 기존 문서의 버전과 주요 변경 사항
- 기능·기술 정책 변경에 따른 관련 문서 수정
- 구현 중 발견된 문제와 개선 내용
- 프로젝트 단계와 후속 작업 현황

ERD·테이블 정의서는 **업로드 후 실제 경로를 기재**하고, AI 아키텍처는 작성 후 별도 소개를 추가합니다. 미등록·작성 중 문서의 세부 내용은 확정 후 업데이트합니다.

## 5. 프로젝트 진행 요약

**2026년 10월 29일 기준**, 프로젝트는 공통 기획·설계 문서의 주요 작성 단계를 지나 기술 명세 보완 및 구현 준비 단계에 있습니다. PRD·TRD·화면정의서·서비스 플로우차트를 개정하고, 기능정의서·시나리오 기획서·기술 아키텍처·API 명세서를 작성했습니다.
